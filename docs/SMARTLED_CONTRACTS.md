# 스마트LED — 기존 LED조명 납품요구 서비스 분리

## 최종 사용자 범위

2026-10-22 사용자가 **“기존 LED조명 서비스랑 동일해”**라고 확인했다.
따라서 기존 나라장터 쇼핑몰 납품요구 서비스와 동일한 원천·저장소·직렬 수집 방식에서 스마트LED만 별도 메뉴로 분리한다.

- 메뉴명: **스마트LED**, `/smartled`.
- 스마트LED 전용 시작일: **2026-10-01 한국시간 포함**.
- 기존 LED/등주 메뉴, 전체 수집 시작일, 일반 완료 체크포인트는 그대로 보존한다.
- 초기 작성한 일반 물품계약 API/전용 테이블/큐/source guard 확대는 최종 변경에서 **제외**했다. 관련 코드는 로컬에만 별도 보존했다. PR 기존 이력은 삭제/강제 갱신하지 않고 추가 커밋으로 범위를 정리했다.

## 같은 서비스의 조회와 분류

기존 `shopping_records`와 기존 정규화/지역/검색 도우미를 재사용한다. 기본 지역은 기존 화면과 같은 인천광역시이며 전국 선택이 가능하다. 날짜·지역·기관/업체/제품/식별번호/모델 검색, 수량·단가·금액 및 조회 KPI를 제공한다. 신규 화면은 메모리 상한을 위해 한 페이지 최대 200건이며 이전/다음으로 조회한다. 합계는 **현재 페이지** 기준임을 표시한다.

일자는 조달청 **납품요구 접수일**이며 계약 체결일·대금 지급일로 표시하지 않는다. 일반 물품계약 전체를 수집한다고 표현하지 않는다. 기존 LED와 스마트LED 등기구가 같은 납품행을 보여줄 수 있으므로 두 메뉴 합계를 더하면 안 된다.

사용자 첨부 표의 정확히 **7개** 세부품명번호만 확정한다:

- 등기구: `3911980201`, `3911980202`, `3911980301`~`3911980304`
- 제어시스템: `3911980401`

**스마트LED램프 `3911980101`은 첨부 범위 밖이므로 이번 저장·조회에서 제외한다.**

일반 LED 코드, 제목에 있는 ‘스마트’ 표현만으로 확정하지 않는다. 제어시스템은 등기구와 별도 조회·합계이고, 제어 단독액을 등기구 납품액에 넣지 않는다. 혼합 납품요구 전체 금액 대신 해당 품목 금액을 표시한다.

공식 근거:
- [조달청 스마트LED 품명 신설](https://www.pps.go.kr/kor/bbs/view.do?bbsSn=2504180012&key=00641) (2025-04-17 적용)
- [기존 쇼핑몰 품목정보서비스](https://www.data.go.kr/data/15129471/openapi.do), `ShoppingMallPrdctInfoService/getDlvrReqDtlInfoList`

## 운영 보존과 한정 재확인

- 새 API·워커·스레드·스케줄·DB 테이블 없음. 기존 메모리 승인된 shopping 직렬 워커에서 기존 일반 수집을 **먼저** 수행한 뒤 스마트LED 전용 재확인 슬롯을 실행한다.
- 기존에 저장된 6종 스마트 등기구는 바로 분리 조회한다. 기존 일반 필터에 없던 스마트 제어시스템는 10월 1일 이후 자료에 한하여 전용 재확인 경로에서 추가 보관한다.
- 전용 `smartled-v1:날짜:날짜` receipt로 1일 범위, 250행×최대 2페이지를 처리한다. 기존 source context/메모리 보호/공유 API quota를 그대로 따른다. 미완료 페이지는 다음 실행에 재개하고, 원천 완전 확인 전 날짜 커서를 넘기지 않는다.
- 최초 순차 확인 후 최근 7일 겹침 구간과 10월 1일부터의 장기 구간을 교대로 순환 재확인한다. 한 슬롯의 1일/2페이지 상한은 그대로이며, 미완료 구간은 같은 lane에서 재개한다. 완료된 전용 receipt만 새 reconciliation generation을 시작하고 부분 진행 receipt를 초기화하지 않는다.
- 기존 일반 범위의 reconciliation은 스마트 전용 제어시스템 레코드를 잘못 비활성화하지 않는다. 스마트 전용 완전 재확인에서 원천에서 빠진 해당 품목은 비활성화한다. 빈 결과나 미완료 응답으로 기존 자료를 삭제하지 않는다.
- 메모리 보류는 기존 워커 상위로 전달하여 다른 원천 할당 전에 중단한다. 스마트 재확인 실패로 성공한 일반 shopping 상태를 실패로 덮어쓰지 않는다.
- 화면은 네트워크/DDL 없이 저장자료만 읽는다. PostgreSQL 조회 timeout 3.5초/work_mem 4MiB, 페이지 200행 상한. 별도 result-only 서버의 스마트 전용 snapshot은 아직 없으므로 명시적 조회 대기로 표시하며 운영 DB 직접 조회로 우회하지 않는다.

## 검증·제한

Work cloud 격리 SQLite와 합성 공식 필드 fixture에서 테스트했다. Python 3.12.14 사용(프로젝트 지원 >=3.11,<3.13).
시작일 경계, 공식 코드, 혼합 품목, 차수/금액 업데이트, 비활성/미확정 납품요구 제외, 페이지 상한, XSS/인증/read-only, 전용 receipt 및 기존 receipt 보존, partial 재개, 일반 reconciliation의 스마트 전용 자료 보존, 겹침 재확인을 검증한다.

운영 키/운영 DB/실수집 건수는 이 작업에서 확인하거나 변경하지 않았다. 실제 원천 누락 없는 전체 수집, 모든 과거 정정의 즉시 탐지, 3년 무제한 운영을 보증하지 않는다. main 병합·운영 배포는 별도 승인 전까지 하지 않는다. 기존 PR·데이터·환경설정은 보존한다.
