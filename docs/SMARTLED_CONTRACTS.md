# 스마트LED 관공서 계약 메뉴 (Draft, 2026-10-22)

## 요청과 범위

- 메뉴명: **스마트LED**, `/smartled`. 기본 탭은 일반 물품계약이며 쇼핑몰 납품요구는 별도 탭이다.
- 스마트LED 전용 시작일: **2026-10-01 한국시간 포함**. 기존 쇼핑몰 전체 수집 시작일/기존 완료 체크포인트는 바꾸지 않는다.
- 물품계약 탭은 **계약 체결일** 기준이다. 쇼핑몰 탭은 **조달청 납품요구 접수일** 기준이며 계약일/지급일로 표시하지 않는다.
- 일반계약 후보 검색은 공식 `prdctClsfcNoNm=스마트LED` 조건이다. 상세 품목에서 확인된 분류만 현재 목록에 표시한다. 명칭 검색의 미탐 가능성이 있으므로 **관공서 스마트LED 계약 전수 수집이 아니다**. 검색 결과 0건/HTTP 접근 실패를 전체 계약 0건으로 해석하지 않는다.
- 물품계약과 쇼핑몰 납품요구에 동일 계약이 존재할 수 있다. 두 탭 금액을 합산하지 않는다. 입찰 공고나 일반 MAS 상품 등록을 실제 납품계약으로 표시하지 않는다.

## 공식 근거와 분류

- [조달청 스마트LED 품명 신설 공지](https://www.pps.go.kr/kor/bbs/view.do?bbsSn=2504180012&key=00641): 2025-04-17 적용.
- [나라장터 계약정보서비스](https://www.data.go.kr/data/15129427/openapi.do).
- [쇼핑몰 품목정보서비스](https://www.data.go.kr/data/15129471/openapi.do).

쇼핑몰 세부품명번호: 램프 `3911980101`; 등기구 `3911980201`, `3911980202`, `3911980301`~`3911980304`; 제어시스템 `3911980401`.
일반 물품계약 상세 API는 8자리 품명번호를 제공한다. `39119801`은 램프, `39119802/39119803`은 등기구, `39119804`는 제어시스템으로 구분한다. 일반 LED 코드나 제목의 ‘스마트’ 문자열만으로 확정하지 않는다. 제어시스템 단독 금액은 등기구 납품액에 포함하지 않는다.

## 계약 원천과 날짜 의미

- `CntrctInfoService/getCntrctInfoListThngPPSSrch`, `inqryDiv=1`, `inqryBgnDate/inqryEndDate`: 계약 체결일 검색. 검색어는 문서화된 **품명** 조건에만 사용하며 존재하지 않는 계약명/숫자 분류 필터를 만들지 않는다.
- `getCntrctInfoListThng`, `getCntrctInfoListThngDetail`, `inqryDiv=2`: 정확한 통합계약번호 `untyCntrctNo` 단건 범위의 현재 헤더/상세 확인.
- `getCntrctInfoListThngChgHstry`: 변경일 구간. 알려진 계약은 스마트라는 명칭이 사라져도 재확인한다.
- `getCntrctInfoListThngDltHstry`: 삭제일 구간. 원천 `DEL`은 현재 목록에서 제외하되 **법적 계약 취소 확정으로 표시하지 않는다**.
- 계약번호 없는 행, 바뀐 totalCount, 미완료 상세, 헤더 변경, 상세 차수 불일치는 현재 자료로 승격하지 않는다.
- 상세 동일 품목 중복행은 실제 별개 수량 행일 수 있어 품목번호로 제거하지 않는다. 완전한 계약 스냅샷으로 원자 교체하며 no-match/시작일 이전 정정은 기존 매칭을 현재 목록에서 내린다.
- `thtmCntrctAmt`는 계약 전체 참고금액이다. 등기구/램프/제어 해당 품목 합계와 구분하고, 미제공 금액은 0원으로 만들지 않는다. 여러 기관/공동업체를 보존한다.

## 기존 운영 구조 보존과 제한

- 새 스레드/워커/크론 없음. 기존 메모리 승인된 shopping 직렬 워커가 일반 수집을 먼저 마친 뒤 스마트LED 슬롯을 실행한다.
- 계약 슬롯: 각 검색/변경/삭제 피드 최대 1페이지(각 100건), 계약 상세 확인 최대 1계약(헤더 2회 + 상세 최대 4페이지). 정상 한 슬롯 최대 9회, 공유 G2B 일일 상한 900회 안에서 동작한다. 페이지/계약별 source context를 좁혀 다른 날짜/계약/엔드포인트는 거절한다.
- 과거 및 전일 구간은 커서로 재개한다. 자정이 지나도 미완료 페이지를 새 전일로 덮어쓰지 않는다. 전체 수집량이 처리량보다 많으면 지연이 남는다.
- 큐 최대 200건. 큐 추가+스캔 커서는 같은 트랜잭션이며 포화 시 커서를 넘기거나 작업을 버리지 않는다. 삭제 뒤 재등록에도 재사용되지 않는 전역 revision으로 오래된 refresh를 차단한다.
- 일반 실패 3회 후 보류하고 24시간 이후 다시 원천에서 관찰되면 제한적으로 재시도한다. 메모리/쿼터/source guard 보류는 일반 실패로 삼키지 않고 상위 워커에 전달한다.
- 공유 API 할당량은 shopping/contract 합계이다. 계약 API 권한 실패가 기존 쇼핑몰 연결상태를 실패로 덮어쓰지 않도록 연결 진단 키를 분리한다.
- 계약 상세 한 번 최대 400행, 원천/정규화 스냅샷 2MiB 제한. 숫자 지수/길이 제한으로 Decimal 포맷의 대형 할당도 차단한다.
- 쇼핑몰 추가 램프·제어는 별도 `smartled-v1` 영수증에서만 보관한다. 기존 정상 수집의 완료 영수증/분류 계약은 그대로 유지한다. 기존 일반 재수집이 스마트 전용 품목을 잘못 비활성화하지 않는다. 최초 순차 확인 후 7일 겹침 구간을 회전 재확인한다. 7일 이전 원천 변경을 빠짐없이 탐지한다고 보장하지 않는다.
- 화면은 최대 100개 요약 레코드, 계약당 각 구분 첫 3품목/4KiB 요약, PostgreSQL 조회 timeout 3.5초/work_mem 4MiB. 전체 상세 JSON 100개를 로딩하지 않는다. 조회 중 DDL·외부 API 호출 없음.
- 신규 테이블은 기존 웹 bootstrap의 additive DDL로 준비한다. 계약당 현재 정규화 스냅샷 1개를 교체하며 매번 원본/변경이력을 복제해 누적하지 않는다. 사업자료 건수 증가에 따른 디스크 사용은 남으며 3년 무제한 운영을 보증하지 않는다. 운영 DB autovacuum/용량 경보는 별도 운영 검증 대상이다.

## 검증 및 아직 하지 않은 것

- Work 클라우드의 격리 SQLite/합성 공식 필드 fixture로 테스트. Python 3.12.14 사용(프로젝트 범위 >=3.11,<3.13). 네트워크는 테스트에서 가짜 transport로 대체한다.
- 시작일 경계, 분류, 혼합 금액, 중복행, 수정/삭제/재등록 revision, 큐 포화/실패 재시도, partial/바뀐 totalCount/자정 커서, 메모리/쿼터 보류, source guard, HTTP XSS/인증/read-only를 검증한다.
- 이 작업 환경에는 G2B 서비스키와 운영 PostgreSQL 연결이 없다. 따라서 **실제 계약 API 이용 권한, 실응답과 명칭 검색의 포괄성, 운영 PostgreSQL 실마이그레이션, 실제 수집 건수는 검증하지 않았다**. 공개 스키마 확인과 mock transport 통과를 실제 수집 성공으로 표현하지 않는다.
- 신규 저장소/계정/서비스 가입 없음. 기존 PR 덮어쓰기/삭제 없음. main 병합·운영 배포·운영 DB 조작·수동 대량 수집 없음.

## 배포 승인 후 별도 확인할 항목

1. 기존 서비스키에 계약정보서비스 권한이 있는지 한정된 읽기 요청으로 확인(사용자에게 키를 채팅으로 요청하지 않음).
2. 계약일 1일 / 후보 1개를 실공식 응답과 대조: 기관·업체·분류·계약번호·금액·최신 차수 및 변경/삭제 의미 확인.
3. DB bootstrap 성공, worker RSS/소스 호출량/큐 지연/디스크 증가를 관찰하고 일반 shopping/budget 수집이 영향을 받지 않는지 확인.
4. 검색어에 잡히지 않는 공식 스마트 분류 사례가 확인되면 별도 근거와 처리량 예산을 정해 bulk 상세 탐색 범위 확장 여부 검토. 현재 코드를 전수 수집 완료로 홍보하지 않음.
