## Policy

- Raw cgroup-v2 `memory.current`, including web and its single source child,
  is compared with **220,000,000 decimal bytes** in a real 268,435,456-byte limit.
- The initial 32MiB startup assumption was disproven by a prior low-pressure
  experiment. The current **52MiB startup reserve is provisional** and is not
  reduced by this supplement. At raw173MiB, startup remains held until a fresh
  sample proves sufficient capacity; effective115MiB is not free raw capacity.
- `G2B_256MIB_DYNAMIC_SOURCE_BUDGET` remains **OFF by default**. Verified larger
  cgroups retain the legacy policy; missing source/limit/current proof fails closed.
- Every bounded read, parser feed, classifier allocation and row write has a
  synchronous fresh-byte preflight, with a separate 2MiB drift allowance. Parent
  sampling is only a backup, not proof that an unbounded allocation is safe.

## Bounded processing and durable resume

- Opted-in source-only JSON/XML uses 16KiB feeds, a 16MiB body ceiling, 1,000-row,
  256-field, 64KiB-field, 128KiB-canonical-row, nesting and node limits. Ambiguous
  duplicate envelopes are rejected. A rejected page receives no successful
  transport attestation or page receipt; a request already begun consumes quota once.
- Stored budget classification selects bounded scalar inputs, checks byte limits
  and masks oversized strings in the same SQL statement before driver decoding.
  It does not load historical amounts JSON. Wide string strip/join/casefold gets
  a size-sensitive reserve. Primary and compatibility writes use one transaction,
  recheck/lock both source hashes, and report progress only after commit.
- Physical classification reads and transactions are one row each. Logical batch
  work limits retain the caller's batch-size and max-batches budget, avoiding a
  500-fold backlog-throughput reduction.
- Pressure inside a page transaction rolls back only that uncommitted page;
  generation, page size, receipts and next durable page are preserved. Child HOLD
  exits and is reaped before another source can enter. It does not wait resident.
- The no-progress latch and generation reservation persist in existing app settings.
  Only current-generation durable progress or real parent-baseline improvement
  can reopen a non-deterministic pressure hold. Ordinary child memory release
  cannot masquerade as parent recovery. Missing/corrupt state stays held. Normal
  archived COMPLETE/SUPERSEDED receipt compaction is excluded from progress proof,
  while active/recent incomplete or inconsistent receipt evidence stays held.
- Deterministic response/row limits use exit79 and a token-scoped operator hold;
  automatic scheduling and key wakes cannot clear it. Scoped authenticated,
  CSRF-protected intervention is distinct from automatic retry. An interrupted
  reservation with unconfirmed reap remains explicitly held rather than assuming
  the old worker has gone away.

## Idle recovery

Eligibility is checked every60seconds, independently of actual collection/GC.
Existing request/download/worker exclusion, 45-second pressure idle requirement,
1-hour pressure-attempt cooldown and 48–72-hour normal interval remain intact.
A check records its skip reason and next due time. Reclaim is bounded file-cache
only and reports denial, partial/no-effect or actual release; requested bytes
never count as evidence. Dynamic partial shortfalls below8MiB can request a
smaller bounded retry (minimum1MiB), still under the same cooldown and idle guards.

## Release evidence required

The dedicated disposable CI must exercise the real parent admission, Popen,
supervision and confirmed-reap path with web and one worker in the SAME256MiB
cgroup, PostgreSQL/telemetry outside, and initial raw173±2MiB/effective115±2MiB.
Anonymous ballast must stay stable and cache must be clean disk-backed data
created/fsynced inside that cgroup, not tmpfs or a host-prewarmed bind mount.
Required scenarios include shopping/budget alternation, reclaim denial/partial/
no-effect, durable no-progress across restart, actual JSON/XML parse/hash/PG
transactions, pressure rollback/exact resume, stable web PID, bounded public HTML
and /live latency, kernel memory.peak below220,000,000 and zero max/oom/oom_kill
event deltas. Synthetic fixture transport uses no public API or production data.

Local unit/SQLite/dialect checks are not real-cgroup or Cafe24 evidence. Actual
Cafe24 memory.reclaim permissions, credentials, live payload distribution and
large authenticated exports remain separate operational uncertainties. Keep this
PR Draft and do not merge, enable the production flag or deploy without the
separate release decision.

## Canary coverage boundaries

The six fresh-container scenarios are JSON, XML, transaction rollback, near-cap
JSON, near-cap XML and no-progress/restart. Normal budget pages retain the
production 1,000-row size (1,000 + 1,000 + 477); shopping retains 999 rows.
The 2,477-row classification backlog uses the real bounded projection and paired
PostgreSQL transaction. Near-16MiB cases prove bounded HOLD, not successful
collection of those oversized-in-memory fixtures.

The parent scheduler/admission/spawn/supervise/reap functions and child entry,
lease, HTTP parser, attestation and database writes are real. CI replaces the
source date/scope orchestration with disposable fixture scopes, so full multi-day
orchestration and the production precollection classification-drain sequence are
not end-to-end evidence. Clock acceleration tests the four-hour scheduling
boundary without claiming four hours of wall-clock endurance. The no-progress
scenario intentionally restarts the web after confirmed reap; the other scenarios
require a stable web PID.

Reclaim denied/no-op/partial are injected faults. Controlled clean-cache removal
then demonstrates admission based on actual lower readings; it does not prove
that Cafe24 grants a successful kernel memory.reclaim write. Public HTML probes
are suspended during the deliberate idle-reclaim fault window, with /live probes
continuing. Authenticated heavy exports and unbounded concurrent traffic are not
covered. Retention regressions executed locally use disposable SQLite; the
separate PostgreSQL/cgroup jobs remain the release evidence gate.
